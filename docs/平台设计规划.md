# 设备管理平台 · 总体设计与实现规划

> 面向：产品/架构/研发。回答「这个平台长什么样、为什么这样分层、现在做到哪、下一步做什么」。
> 插件对接细节见《插件开发规范》，安装与运维见《部署运维手册》。

---

## 1. 目标与边界

### 1.1 一句话定位

在 Linux 设备（Ubuntu 20.04/22.04，x86_64 / arm64）上交付一个**单二进制、零外部依赖**的 Web 平台：

- **管设备**：把操作系统的网络、主机、安全、日志能力做成可视化配置；
- **装能力**：用统一的插件市场把自研/二次开发的功能（含容器化应用）纳入同一套生命周期管理；
- **好交付**：一个安装目录装下全部数据，一键安装成 systemd 服务，支持出厂预装与离线升级。

### 1.2 设计约束（决定了所有技术选型）

| 约束 | 后果 |
| --- | --- |
| 设备长期无人值守、可能无外网 | 不允许依赖 MySQL/Redis/外部服务；数据库用嵌入式 SQLite |
| 设备 ARM/x86 混合、算力有限 | 后端 Go 单静态二进制（CGO 关闭），前端内嵌；采集周期可调、日志按天滚动 |
| 要能整机备份/换机迁移 | 数据库/日志/插件/上传文件全部收敛到 `app.home` 一个目录 |
| 设备现场人员不懂 Linux | 常用能力必须可视化，且每个下发动作要**逐项回报成功/失败原因**，不能静默失败 |
| 第三方/自研功能要能持续叠加 | 插件与平台解耦：只约定 manifest + 约定目录，平台不感知插件内部实现 |

## 2. 技术架构

### 2.1 分层

```
┌────────────────────────────────────────────────────────────┐
│  Web 前端（Vue3 + Element Plus + Tailwind，内嵌进二进制）    │
│  后端菜单驱动路由：GET /api/v1/auth/routes → ComponentLoader │
└───────────────────────────┬────────────────────────────────┘
                            │ REST /api/v1/**（JWT + RBAC + 操作日志）
┌───────────────────────────┴────────────────────────────────┐
│  Gin 路由层  internal/router                                │
│  中间件：Trace / Recovery / CORS / Auth / Perm / AccessLog   │
│          / OperLog（字段级 diff）/ Metrics / RateLimit       │
├─────────────────────────────────────────────────────────────┤
│  业务层  internal/service（唯一的业务规则所在地）             │
│   host / network / device / security / plugin / log / alerts │
├─────────────────────────────────────────────────────────────┤
│  能力层                                                     │
│   sysinfo（gopsutil 采集）  syscmd（受控命令执行）            │
│   plugin（插件框架：安装/配置渲染/进程与容器运行时）           │
│   storage（本地磁盘/OSS）   cache（进程内 KV+集合+租约）      │
├─────────────────────────────────────────────────────────────┤
│  数据层  repository(GORM) → SQLite（WAL）                    │
│  迁移唯一入口：migrations/*.up.sql（内嵌，版本化执行）        │
└─────────────────────────────────────────────────────────────┘
                            │
                    操作系统（iproute2 / iptables /
                    firewalld / tc / systemd / timedatectl）
```

### 2.2 目录即约定（统一数据目录）

```
/opt/device-platform/            ← app.home（-d 参数 / DEVPLAT_HOME）
├─ bin/device-platform           平台二进制
├─ conf/config.yaml              配置（首次启动自动生成）
├─ data/device-platform.db       SQLite（含 -wal/-shm）
├─ logs/                         平台日志（按天滚动）
├─ plugins/<id>/<version>/       已安装插件包（解压态）
├─ plugins-bundled/<id>/         随平台分发的插件（市场里「可安装」）
├─ plugin-data/<id>/             插件运行数据：conf/ logs/ 自定义持久化
├─ storage/                      平台上传的文件（/static 直出）
├─ backup/                       升级前的二进制/数据库备份
├─ run/  tmp/                    pid 与临时解压目录
```

**为什么这样重要**：设备换机 = 打包 `home` → 解压到新机 → 改 `install.sh --port` → 起服务。

### 2.3 数据库选型与 SQLite 落地要点

| 项 | 做法 | 原因 |
| --- | --- | --- |
| 驱动 | `github.com/glebarez/sqlite`（modernc 纯 Go） | 无需 cgo，能交叉编译到 arm64 |
| 模式 | WAL + `busy_timeout=10s` + `_txlock=immediate` | 读写并发、避免瞬时锁冲突 |
| 时间 | `_timezone` / `_time_format=sqlite`，列类型保留 `DATETIME` | 驱动按声明类型解析为 `time.Time`，避免时区错位 |
| 迁移 | `CREATE TABLE IF NOT EXISTS` + 索引独立建；表内不写 `KEY`/`ENGINE` | SQLite 方言差异，已全部转换（脚本 `scripts/migrate-to-sqlite.py`） |
| 连接数 | `max_open=4` | 写锁竞争小于并发收益 |

> 原 MySQL 方言迁移已一次性转换完毕（含 `IFNULL`/`CONCAT`/`DATE_FORMAT` 等语句改造），
> 后续新增迁移**只写 SQLite 方言**。

### 2.4 缓存：从 Redis 到进程内

原来的 Redis 承担 6 类职责，逐一替换：

| 原职责 | 现在实现 | 影响 |
| --- | --- | --- |
| 登录会话 / 双 token 校验 | `pkg/cache` 内存 KV + TTL | 进程重启后用户需重新登录（设备场景可接受） |
| 在线用户集合 | 内存 Set | 同上 |
| 图形验证码 | `pkg/captcha.MemoryStore` | — |
| 接口限流 | 内存计数器（滑动窗口） | 单机场景等价 |
| 权限缓存（principal） | 内存 KV，版本号失效 | — |
| 定时任务租约 | 内存租约锁 | 单机单副本，语义等价 |

## 4. 关键设计决策

### 4.1 为什么「配置态 + 下发」而不是直接改系统

设备网络一旦改错就失联。平台的策略是：

1. 所有变更先落库（期望态），页面可审阅、可回滚；
2. 「下发」是显式动作，逐条执行并返回 `{item, ok, message}`；
3. 平台只操作**专属命名空间**（`DEVPLAT_*` 链、平台自建 qdisc），不动系统既有规则；
4. 下发失败不阻断保存，用户能看到哪一条、为什么失败。

### 4.2 命令执行安全模型

- 所有系统命令集中在 `internal/syscmd`：统一超时、输出采集、错误可读化；
- 参数走**白名单正则**（目标地址、网卡名、tcpdump 过滤表达式），拒绝参数注入；
- 需要特权的功能先检查 `isRoot()`/Linux 环境，非 Linux 或非 root 返回可读提示而不是 500；
- systemd 单元只授予 `CAP_NET_ADMIN/CAP_NET_RAW/CAP_NET_BIND_SERVICE`。

### 4.3 插件为什么用「约定目录 + manifest」而不是插件 SDK

设备上跑的多是**已有程序的二次封装**（frpc、dnsmasq、ffmpeg、自研采集器），要求它们引入 SDK 不现实。
因此平台只做四件事：**解压校验 → 渲染配置 → 拉起/停止进程或容器 → 收集日志**。
好处是任何语言、任何既有程序都能被托管；代价是平台不感知插件内部状态（用健康检查与日志弥补）。

### 4.4 错误必须可读

沿用脚手架约定：业务错误用 `errs.Invalid("原因")`，前端优先展示后端 `message`。
本次新增的下发类接口还会返回逐项结果，避免「保存成功但没生效」的错觉。

### Phase 3（3～6 个月）— 从「工具」到「行业方案」

1. **采集与上报**：内置 MQTT/HTTP 上报插件模板，支持「边缘采集 → 云平台」。
2. **零信任接入**：WireGuard 插件 + 设备证书自动签发（与 frp 互补，替代公网端口暴露）。
3. **AI 边缘**：摄像头/音视频类插件（YOLO 推理、RTSP 转 WebRTC），平台提供 GPU/NPU 占用看板。
4. **多机管理**：设备侧保持单机自治，另出「中心侧」做批量配置下发（复用插件包与策略模型）。
5. **开放 API / Webhook**：策略变更、告警、插件状态事件外推，供行业平台集成。
6. **插件依赖与版本回滚**：索引声明 `dependsOn`、安装前依赖检查、一键回滚上一版本。
7. **多实例插件**：同 id 多实例（每实例一套配置/端口），适配「同款程序跑多个站点」。

## 6. 行业扩展思路（怎么讲清「能装在很多行业」）

平台的通用骨架是：**设备状态可视 + 网络可配 + 能力可插 + 无人值守可交付**。
换行业时变的只是「装哪些插件、开哪些策略、接哪个平台」。

| 行业 | 典型设备 | 关键插件/能力 | 平台卖点 |
| --- | --- | --- | --- |
| 工业网关/边缘计算 | 工控机、ARM 网关 | Modbus/OPC-UA 采集插件、MQTT 上报、本地时序缓存 | 现场协议转换 + 断网续传，一根网线交付 |
| 智慧园区/安防 | NVR 一体机、边缘盒 | RTSP 转 WebRTC、人形检测、视频存储清理 | 视频能力插件化，按需授权 |
| 连锁门店/无人零售 | 收银一体机、边缘路由 | 收银外设代理、远程桌面、frp/WireGuard 回传 | 门店零 IT，总部远程运维 |
| 医疗/检验设备 | 检验仪、影像工作站 | DICOM 转发、串口协议插件、审计留痕 | 合规日志 + 内网穿透 + 数据不出院 |
| 车载/轨交 | 车载终端 | 4G/5G 多链路切换、GPS 上报、离线升级 | 弱网可用、断网自治 |
| 能源/充电桩 | 充电桩控制器 | OCPP 插件、计费对接、远程升级 | 标准协议插件化，快速对接运营平台 |
| 教育/实验室 | 实验箱、教学网关 | 环境镜像管理、沙箱容器、课程插件 | 一台设备=一个实验环境 |
| 农业/水利 | 田间网关、水文站 | LoRa/RS485 采集、太阳能电量监控、断网缓存 | 低功耗、远程诊断 |

> 交付话术建议：不要卖「后台管理系统」，而是卖「**设备交付底座**」——
> 出厂预装（一条命令）、现场零配置（扫码/默认策略）、能力按需（插件市场）、
> 运维远程（穿透+日志+告警）、升级可控（离线包 + 回滚）。

## 7. 非功能设计

| 维度 | 现状 / 规划 |
| --- | --- |
| 性能 | 指标采集默认 10s；SQLite 单文件，日志类表按保留天数清理（默认 30 天） |
| 可靠性 | systemd `Restart=on-failure`；插件按 `restartPolicy` 自动拉起；数据库 WAL + busy_timeout |
| 安全 | JWT 双 token；RBAC 到按钮/接口级；操作日志含字段级 diff；敏感字段脱敏；插件包解压防穿越、限大小 |
| 可观测 | `/healthz` `/readyz` `/metrics`（Prometheus 文本）；页面内「系统日志」与「访问日志」 |
| 可维护 | 迁移版本化（唯一的建表入口）；代码生成器可产出 CRUD 骨架；两套零依赖 E2E 脚本 |
| 兼容 | 交叉编译 amd64/arm64；插件 manifest 可声明 `arch` 限制；docker 运行时可选 |

## 8. 与脚手架的差异清单（给接手同学）
